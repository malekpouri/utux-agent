# M0 — Foundations and evaluation protocol

Execution plan for milestone M0 of utux Agent. Save as `docs/plan/M0.md`.

**Goal.** A repository in which a valid project can be created, every file
contract has a schema, a model call is logged with its cost, and the
evaluation protocol is committed before any system result exists.

**Exit criteria** (from the specification, section 12):

- [x] `utux init` creates a valid project.
- [x] A model call is logged to `events.jsonl` with tokens and cost.
- [x] The evaluation protocol is committed and tagged before any result exists.

**Out of scope for M0.** LangGraph, the Docker executor, agents and prompts,
literature sources, verification logic, routing escalation, staleness
tracking. These belong to M1–M3.

**Owner tags.** `[agent]` can be done by the coding agent. `[human]` must be
done by a person; the agent may prepare tooling but not the content.

Each task is sized for roughly half a day to one day. Take tasks in order
unless the dependencies say otherwise.

## B. File contracts

All schemas are Pydantic v2 models in `utux.schemas`, each with a
`schema_version` field, valid and invalid fixtures, and a round-trip test.
Field lists come from the specification section 7 and RFC-001 section 6.

### M0-03 Project configuration schema `[agent]`
Depends on: M0-01.

`utux.yaml`: profile, domain pack, total and per-stage budget in USD,
oversight mode (`guided` or `auto`) with per-gate switches, verification
toggle, AI-disclosure drafting toggle, data policy (`external_allowed` or
`local_only`), resource limits, role-to-tier and tier-to-model mapping.

Acceptance criteria:
- [x] A minimal file with only required fields validates and fills documented defaults.
- [x] Defaults are: oversight `guided`, verification on, data policy stated explicitly (no default; missing value is an error).
- [x] Unknown keys are rejected with an error naming the key.
- [x] The final-manuscript gate cannot be switched off; attempting it is a validation error.
- [x] At least five invalid fixtures, each failing for a different, asserted reason.

### M0-04 Artifact metadata and hashing `[agent]`
Depends on: M0-01.

Sidecar model: `artifact_id`, `stage`, `schema_version`, `created_by`,
`created_at`, `input_artifacts`, `content_hash`, `state`. A hashing utility
for files and directories.

Acceptance criteria:
- [x] The hash of a file is stable across runs and platforms (tested on fixed bytes with a written-out expected value).
- [x] The directory hash is independent of file-system ordering.
- [x] `state` accepts only the documented values.
- [x] The example in the specification section 7 validates unchanged.

### M0-05 Event schema and event log `[agent]`
Depends on: M0-04.

Event model with all fields of the specification (ids, parent id, actor,
stage, type, model, prompt and tool version, input and output hash, tokens,
cost, duration, status, retry reason, escalation, artifacts). An `EventLog`
with `append()` and an iterator.

Acceptance criteria:
- [x] `append()` writes exactly one line, ends it with a newline and flushes to disk.
- [x] Event ids are unique and increasing within a project.
- [x] The log is never opened in a mode that can truncate it (asserted by test).
- [x] A partially written last line (simulated crash) is detected and reported on read, not silently dropped.
- [x] Reading 10,000 events streams without loading the file into memory.
- [x] An event with an unknown `type` is rejected.

### M0-06a Claim ledger and result record schemas `[agent]`
Depends on: M0-04.

Claim ledger entry (RFC-001 section 6, ordinal confidence, four scientific
statuses plus `unverified`), evidence entries (`source` with scope flags,
`result_record`, `claim`) and the result record.

Acceptance criteria:
- [x] The JSON examples in the specification and RFC-001 validate unchanged; if one does not, stop and report the mismatch.
- [x] `status`, `confidence`, agreement labels, scope flags and reasons are closed enumerations taken from RFC-001.
- [x] A ledger entry with `confidence: high` or `confidence: medium` and a status other than `verified` is rejected.
- [x] A `verified` literature claim with no evidence entry is rejected.
- [x] A literature claim takes only `source` evidence, a result claim only `result_record` evidence and a derived claim only `claim` evidence.

### M0-06b Run manifest, approval and source record schemas, and schema export `[agent]`
Depends on: M0-06a.

Run manifest, approval request and response, source record (identifier, URL,
licence, redistribution permission, retrieval date, text hash, extraction
method and quality), and `utux schema export`.

Acceptance criteria:
- [x] Each of the four contracts has a schema with valid and invalid fixtures and a round-trip test.
- [x] The field lists are proposed in the pull request for the maintainer's review, since the documents give no JSON example for these contracts.
- [x] `utux schema export <dir>` writes one JSON Schema file per contract.

## C. Workspace and CLI

### M0-07 Atomic writer and `utux init` `[agent]`
Depends on: M0-03, M0-05.

Atomic file writer (temporary file in the same directory, then rename).
`utux init <dir>` creates the project tree of the specification section 7,
writes `utux.yaml`, initialises a git repository with a first commit and
appends a `project_created` event.

`utux init` takes `--budget-usd` and `--data-policy` as required options;
neither has a default.

Acceptance criteria:
- [x] The created tree matches the specification; a test compares it to an expected listing.
- [x] `utux init` on a non-empty directory fails with a clear message and changes nothing.
- [x] Interrupting a write (simulated) never leaves a partial contract file.
- [x] The first event is `project_created` with a valid schema.
- [x] The project contains no machine-specific absolute paths.

### M0-08 `utux validate` `[agent]`
Depends on: M0-06a, M0-06b, M0-07.

Validates every contract file in a project against its schema and reports
all problems, not only the first.

Acceptance criteria:
- [x] A fresh project validates with exit code 0.
- [x] Each corrupted fixture project yields a non-zero exit code and a message naming the file, the field and the reason.
- [x] A project written by a newer `schema_version` is refused with a message that says so.
- [x] `--json` prints a machine-readable report.
- [x] A project without `events.jsonl` fails validation.
- [x] Ids are unique across the lines of `claims.jsonl` and of `results.jsonl`; every `result_record` and `claim` evidence id refers to an existing line.

### M0-08b `utux log repair` `[agent]`
Depends on: M0-08.

Repairs an event log whose last line was left incomplete by an interrupted
write. It moves the incomplete last fragment to `events.jsonl.fragment-<ts>`,
restores the log to its last complete event, and appends a `log_repaired`
event with the fragment's hash and byte length. It is never automatic: it
runs only when the user asks for it.

Acceptance criteria (written when the task was taken, for the maintainer's review):
- [x] On a log whose last line is incomplete, the fragment is saved byte for byte to `events.jsonl.fragment-<ts>`, the log ends with its last complete event, and the next event is `log_repaired` with the fragment's file name, hash and byte length.
- [x] Complete lines are never changed: the bytes of the log before the fragment are identical after the repair.
- [x] On a log whose last line is complete, nothing changes and no event is written.
- [x] Nothing repairs the log except `utux log repair`: appending and validating still refuse or report an incomplete last line.
- [x] If the fragment cannot be saved, or the last complete line is not a valid event, the log is unchanged.
- [x] An existing fragment file is never overwritten.
- [x] After the repair, `utux validate` passes on a project that was valid apart from the fragment.
- [x] `utux validate` reports a fragment side file that no `log_repaired` event records, and a `log_repaired` event whose side file is missing or does not match its hash and length.
- [x] On a log whose last line is complete, a fragment side file that no `log_repaired` event records gets its missing `log_repaired` event, and the command reports that an interrupted repair was completed.

## D. Model access and cost

### M0-09 `ModelProvider` interface and conformance suite `[agent]`
Depends on: M0-01.

The Protocol, request and response types (messages, role, usage, cost,
model id, finish reason), typed errors (authentication, rate limit, timeout,
invalid response), and a scripted fake provider for tests.

Acceptance criteria:
- [x] The conformance suite runs against the fake provider and passes.
- [x] The suite checks: usage is always present; cost_usd is always a field and is null when the provider reports no cost; errors map to the typed exceptions; a timeout is honoured.
- [x] The interface has no provider-specific parameter.

### M0-10 OpenRouter provider `[agent]`
Depends on: M0-09.

Implementation on the Python standard library only (ADR-0008): one
OpenAI-compatible chat-completions client, blocking, with the request timeout
honoured. The OpenRouter provider is that client with OpenRouter's base URL
and the key from `OPENROUTER_API_KEY`. The same client works for any
OpenAI-compatible base URL. Retries with backoff on rate limits and transient
errors, bounded.

Acceptance criteria:
- [x] Passes the conformance suite using synthetic, hand-written responses.
- [x] A missing key raises the authentication error before any network call.
- [x] `cost_usd` is only what the provider reports in its response. If the response carries no cost, `cost_usd` is null, never an estimate.
- [x] `is_external` is derived from the configured host: loopback is local, every other host is external.
- [x] The client works for any OpenAI-compatible base URL, tested against a loopback server, which also shows that the timeout is honoured.
- [x] No module of utux accesses the network when it is imported (tested).
- [x] One `live` smoke test exists and is skipped without the key.
- [x] The key never appears in any log, event, exception text or fixture (asserted by test).

### M0-11 Logged model calls and `utux model ping` `[agent]`
Depends on: M0-05, M0-10.

A wrapper that emits one `model_call` event per provider call, with hashes
of input and output, tokens, cost, duration, status and prompt version.
`utux model ping --tier light` sends a fixed short prompt inside a project
and prints tokens and cost.

Acceptance criteria:
- [x] One call produces exactly one event, on success and on failure. A call whose response carries no cost has `cost_usd: null`; that event is the record, and no separate warning event is written.
- [x] A `model_call` event carries `data` `{"provider": <name>, "is_external": <bool>}`, both required, so the log shows which provider received which content hash.
- [x] A failed call has status `error` and a `status_reason` per error type: `model_timeout`, `model_rate_limit`, `model_unavailable`, `model_authentication`, `model_request_rejected`, `model_invalid_response`.
- [x] Under data policy `local_only`, a call to an external provider is refused: a `model_call` event with status `refused` and `status_reason` `data_policy_local_only`, and no network call.
- [x] Message content is not stored in the event, only its hash.
- [x] This satisfies the exit criterion "a model call is logged with cost".

### M0-12 Cost accounting and budget stop `[agent]`
Depends on: M0-11.

Sums cost from the `model_call` events of the log. `utux cost` prints totals
per stage and per actor, with `--json`. A call that would start after the
project budget, or the budget of its stage, is exhausted is refused before
any network call.

Acceptance criteria:
- [x] Totals from a fixture log equal hand-computed values written in the test.
- [x] A null cost from a local provider (`is_external` false) counts as zero and is shown as "local, not billed".
- [x] A null cost from an external provider is unknown: it is shown separately with the number of calls, and `utux cost` states that the budget cannot be fully enforced while such calls exist.
- [x] The budget stop compares the known cost with `budget.total_usd`. When it is exhausted, the next call is refused before any network call: a `model_call` event with status `refused` and `status_reason` `budget_exhausted`, and a `budget_warning` event whose `data` holds `spent_usd` and `total_usd`.
- [x] Per-stage budgets are enforced the same way when the call has a stage.
- [x] `utux cost` prints totals per stage and per actor, and the same as JSON with `--json`.

## E. Evaluation groundwork

### M0-13a Gold item schema and group-aware split `[agent]`
Depends on: M0-06a.

In `utux.evalkit`, with the standard library only (no numpy or scipy): the
gold item schema (RFC-002 section 4) with a validator, a group-aware split
by `source_group` (RFC-002 section 6), and a split report.

Acceptance criteria:
- [x] The gold item schema follows RFC-002 section 4: two-phase annotation with raw labels per claim and per pair, `adjudicated` wherever the raw entries differ at that level, `ambiguous` per claim, `hidden` by origin, and `hard_case` from the codes of section 3. It has valid and invalid fixtures, each invalid one with its expected field and code, and a round-trip test.
- [x] A release is checked across items: unique ids, perturbed items whose origin exists, and splits that keep groups and origins together.
- [x] No `source_group` appears in both splits (tested on a fixture, including a perturbed item and its origin).
- [x] A split report gives, for each split, the counts per gold status, scope flag, domain, evidence text, item source and hard case, and the actual dev share. It reads labels only to count them and prints no item text. A seed is chosen from this report before any system output has been scored (documented).
- [x] Every expected value in the tests is written out and derived independently of the code.
- [x] All fixtures are synthetic and named as synthetic. No reference label is created, inferred or edited that could be mistaken for real annotation.

### M0-13b Agreement, metrics and intervals `[agent]`
Depends on: M0-13a.

In `utux.evalkit`, with the standard library only: annotator agreement (raw
agreement, confusion table, Cohen's kappa, Gwet's AC1, span overlap F1 and
IoU); metric computation (per-label precision, recall, F1, macro-F1,
false-verified rate, critical miss rate, verified coverage, review load,
failure rate) on the units of RFC-002 section 7; exact binomial intervals and
a cluster bootstrap with a fixed seed.

Acceptance criteria:
- [x] Every metric is tested on a small hand-built example with the expected value written in the test and derived independently of the code.
- [x] Claim-level metrics count a multi-source claim once (tested).
- [x] The exact binomial interval is correct for zero observed errors: the upper bound is 1 - (alpha/2)^(1/n).
- [x] The cluster bootstrap gives the same result for the same seed.
- [x] `ambiguous` items are excluded from primary metrics and returned separately.
- [x] The toolkit has a mode that returns metrics only and never prints labels.
- [x] All fixtures are synthetic and named as synthetic.

### M0-13c Gold schema: notes, adjudication reasons, claims without sources `[agent]`
Depends on: M0-13a.

Acceptance criteria:
- [x] A claim may have no pairs only when its status is `insufficient_evidence`; then both raw statuses are `insufficient_evidence` too.
- [x] Each annotator's raw entry for a claim and for a pair has `note`, text or null.
- [x] Claim extraction, each claim and each pair have `adjudication_reason`: text when `adjudicated` is true, null otherwise.
- [x] RFC-002 section 4 matches the schema (own commit).
- [x] `docs/eval/example-item.md` is added as given; a test checks that its JSON validates and that its `text_hash` matches its source text.

### M0-14 Evaluation protocol document `[human]`, drafted by `[agent]`
Depends on: M0-02.

`docs/eval/protocol.md`: hypotheses H1–H5 with the experiment that can refute
each; metric definitions with unit and denominator; initial thresholds; the
three-stage lock procedure of RFC-002 section 8.

Acceptance criteria:
- [x] Every definition is traceable to a section of the specification or RFC-002; nothing new is introduced.
- [x] Reviewed and approved by the maintainer.
- [x] Committed and tagged `eval-protocol-v0` before any system output has been scored.

### M0-15 Annotation guideline and gold set v0 `[human]`
Depends on: M0-13b, M0-14.

Written annotation guideline (draft: [annotation-guideline.md](../eval/annotation-guideline.md), version 0.1); calibration round; selection of open-access
sources with licence records; about 150 claims labelled by two independent

Acceptance criteria:

- [ ] The release has a version, a content hash and a changelog.

### M0-15c Perturbations, v0 sample and audit tooling for gold v0 `[agent]`

- [x] `utux gold audit export` writes a blind sheet of 30 items (20 of model-written types, 10 imported) by a fixed seed. `utux gold audit score` computes Cohen's kappa against the constructed labels, flags kappa below 0.6, and upgrades confirmed items to `confirmation: audit`.

## Gold set v0: remaining work

Gold set v0 is not frozen. Its remaining work is M0-15, a `[human]` task.
Owner of every item: the maintainer. The coding agent writes, suggests and
changes no label (`AGENTS.md` section 8); it may build tooling on request.

1. Review the annotation guideline (`docs/eval/annotation-guideline.md`,
   version 0.1 draft) with the adjudicator.
2. Recruit two annotators per domain and one senior adjudicator who are
   independent of the system (RFC-002 section 5).
3. Choose how annotators work: the annotation tooling of M0-15a
   (`docs/annotation-tooling.md`) gives batches, an offline page and the
   merge into gold items; another process must produce gold items in the
   schema of `docs/gold-set.md`, with citations on every extracted claim.
4. Select open-access sources and write their licence records (RFC-002
   section 2).
5. Run the calibration round on 30 items that are not released; revise the
   guideline, raising its version; repeat while a label stays below the
   kappa floor of 0.6 (RFC-002 sections 5 and 8).
6. Label about 150 claims in two phases, compute agreement before
   adjudication (`annotation_agreement`), then adjudicate with written
   reasons.
7. Split by source group: choose the seed from `split_report` before any
   system output is scored; the adjudicator holds the `test` split outside
   the main repository.
8. Freeze the release: it passes `read_gold_release` and `check_release`
   with no problems, every departure reviewed; it has a version, a content
   hash and a changelog.
9. Lock the H3 thresholds after the pilot and tag `eval-protocol-v0.1`
   (`docs/eval/protocol.md`, section 6).

## Retrospective

### What was unclear in M0

- **Shapes shown only by example.** RFC-002's gold item example left the
  unit of raw labels (per item, per claim or per pair), the value sets of
  `domain`, `origin` and `hard_case`, and claims without sources open. The
  schema was reshaped three times (M0-13a, its review, M0-13c) before the
  two-phase annotation, citations and adjudication reasons settled it.
- **Where a rule's level is.** "Ambiguous" was per item in one place and per
  claim in another; "adjudicated wherever the raw entries differ" needed a
  field on pairs that the given shape did not have.
- **Ambiguous phrases in metric definitions.** "Overlap by at least half"
  (of which span), the token rule for span overlap, what an undefined ratio
  is, and how macro-F1 treats a label neither side used all had to be chosen
  by the agent and confirmed afterwards.
- **One-sided against two-sided intervals.** RFC-002 section 3 sized the
  critical-miss set with a one-sided bound while section 8 used a two-sided
  one; only computing the bound showed it. Numbers in documents are now
  checked by tests.
- **Cost semantics.** Whether a null cost is zero or unknown, whether a
  failed call is billed, and the limits of the budget stop (overshoot,
  parallel calls, providers without cost) were decided in review, after
  implementation.
- **Schema versions before a release.** The rule for changing a schema used
  by committed fixtures needed the pre-release exception of `AGENTS.md`
  section 11.
- **Live calls.** A live test was run once by the agent in M0-10 with a key
  in the environment, which made one paid call; the rule "never run live
  tests" was added afterwards.
- **Specification against RFCs.** The specification and the RFCs differed on
  threshold timing, the refutation of H3, metric names and claim support.
  The rule "the more precise RFC governs, and the specification follows" was
  stated only at the end of M0.
- **The tag.** `eval-protocol-v0` was first pushed before the protocol was
  merged; the M0 plan did not say which commit to tag.
- **Fixture generators.** Synthetic fixtures were generated by a script kept
  outside the repository and lost; later changes were made by a migration
  script. It is unclear whether generators belong in the repository.

### What the M1 plan should state more precisely

- **Event data keys** for every event type M1 emits (`stage_start`,
  `stage_end`, `code_execution`, `tool_call`, `approval_requested`,
  `approval_answered`, `error`), and their status reasons, before the tasks
  that write them.
- **The shapes of new contracts** as complete examples, not partial ones:
  `metrics.json` (types, units, the form of `tolerance`), the approval kinds
  of ADR-0011, the sidecar's `path`, and the new `utux.yaml` keys.
- **Staleness.** M1-11 marks outputs `stale` after an `edit`, while the
  specification places staleness in M3 and the M0 plan put it out of scope.
  Say which part of staleness M1 builds.
- **The project lock** (M1-05): which commands are writers (does
  `utux model ping` or `utux log repair` take it; does `utux cost`), what
  the lock file holds, and how a dead holder is detected on each platform.
- **Budget (a) and (c)** against M0-12's categories: how
  `budget.allow_unknown_cost` treats "failed, not billed" and local calls,
  and how totals kept in memory stay right when a call is refused.
- **"The same results"** in check 1 (M1-10): exact equality of result
  records, or equality within each record's tolerance; where and how the
  process is killed.
- **Docker in the agent's environment:** whether the agent may run
  `docker`-marked tests locally, the CI runner for them, and what counts as
  done when the agent cannot run them.
- **The dependency report** (M1-02): how packages are counted (all
  transitive runtime packages), which versions, and which sources count for
  security incidents.
- **Decisions and tags:** who marks an ADR `Accepted` and where; and for any
  tag or release, the exact commit it goes on.
- **Which text governs** when the M1 plan and the specification differ, as
  stated for the RFCs at the end of M0.
