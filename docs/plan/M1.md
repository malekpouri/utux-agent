# M1 — Execution spike

Execution plan for milestone M1 of utux Agent. Save as `docs/plan/M1.md`.

**Goal.** Stages 3 to 5 (methodology, implementation, experiment) run as one
graph on LangGraph, with model-written code executed only in the hardened
Docker sandbox, every run recorded in a manifest, every number stored as a
result record, and every pause, resume and crash handled from the project
files. The spike also decides whether LangGraph stays.

**Exit criteria** (from the specification, sections 6 and 12):

- [x] Check 1: a run killed in the middle resumes from the SQLite checkpoint and finishes with the same results as an uninterrupted run. M1-10, `test_workflow_kill_and_resume.py`.
- [x] Check 2: a run pauses at an approval gate, the process exits, and a later `utux run` resumes after the approval is answered. M1-11 and M1-14, `test_gates.py` and `test_run_cli.py`.
- [x] Check 3: a finding from a check after the experiment routes the run back to an earlier stage, within the retry cap. M1-12, `test_routing.py`.
- [x] Check 4: every stage, model call, code execution and approval of a run appears in `events.jsonl` while the run is in progress. M1-15b, after it was ticked too early in M1-10.
- [x] ADR-0012 records the orchestration decision: LangGraph confirmed, or the fallback of ADR-0001 taken. LangGraph confirmed; accepted on 2026-11-21.
- [x] The sandbox security tests pass on Linux with Docker. The `docker` CI job runs them on every pull request.
- [x] The maintainer runs the toy task (M1-16) end to end with a real model in `guided` mode, and `utux validate` passes on the resulting project. Done: the maintainer's note of 2026-11-22: `utux run` exited 0 with 7 result records; `utux validate` passes on `../utux-toy` (16 contract files); total cost 0.00282495 USD for 12 calls; `runs/r001` has `manifest.json` and outputs; `results.md` cites R0005, R0006 and R0007 with values equal to `results.jsonl` and adds no context the records do not state.

**Starts when** M0-13b and M0-16 are merged. The human tasks M0-14 and M0-15
continue in parallel; M1 does not need the gold set.

**Out of scope for M1.** Stages 1, 2 and 6, literature sources, claim
verification, the reviewer agents, tier escalation, parallel model calls,
remote and cloud executors, the web dashboard, the bio pilot pack.

**Owner tags.** `[agent]` can be done by the coding agent. `[human]` must be
done by a person. `[decision]` needs the maintainer's acceptance before the
tasks that depend on it start.

**Environment.** Tests that need Docker are marked `docker` and are
deselected by default, like `live`. CI gets a separate job that runs them on
a Linux runner. The coding agent may run them (rule 7). If Docker is not
available to it, it says so and writes those tests without running them; the
maintainer runs them.

## Rules for M1

These answer the retrospective of M0 (`docs/plan/M0.md`). They apply to
every M1 task.

1. **Events.** A task that writes a new event type or new data keys defines
   them in the event schema and in `docs/event-log.md` in the same pull
   request.
2. **File formats.** Every new or changed file format has a complete valid
   example in its docs and in the specification, checked by a test.
3. **Staleness is marking only.** When a new version of an artifact is
   approved, the sidecars of artifacts built from the old version become
   `stale`, and the next stage does not start until they are rebuilt. Any
   other staleness rule is M3.
4. **The project lock.** Every command that writes to a project takes the
   project lock: `utux run`, `utux approve`, `utux log repair`,
   `utux model ping` and any later writer. Read-only commands
   (`utux validate`, `utux cost`, `utux status`, `utux schema export`) do
   not.
5. **`budget.allow_unknown_cost`.** After the first successful call to an
   external provider returns `cost_usd` null, later calls to that provider
   in the project are refused with `unknown_cost_not_allowed`, unless the key
   is true. Local calls, and failures that count as not billed, never
   trigger it. The `ModelProvider` interface does not change.
6. **"Same results" for check 1.** With the scripted model and executor,
   every artifact's content hash and every result record's value are
   identical; the event log differs only by the events of the crash and the
   resume.
7. **Tests.** The agent may run tests marked `docker`. It never runs tests
   marked `live`.
8. **The LangGraph report** counts every runtime package added to `uv.lock`,
   transitive ones included, and lists each with its version and licence.
9. **ADRs.** Only the maintainer accepts an ADR. The agent writes it as
   `Proposed` and changes the status only after an explicit approval in a
   message, citing its date.
10. **Tags.** Only the maintainer tags, and only on a merge commit on `main`
    whose CI passed. The agent names the commit; the maintainer checks it
    with `git ls-remote`.
11. **Precedence** is ADR, RFC, specification, plan. A plan task that departs
    from the specification on purpose says so, and the specification is
    updated in the same pull request. An undeclared difference: stop and
    report.

## A. Decisions and dependencies

### M1-01 Decision records for the open M1 notes `[agent]` `[decision]`
Depends on: none.

The M0 plan left seven notes for M1. Write one ADR for each, with status
`Proposed`, the recommendation below, and the alternatives. The maintainer
accepts or changes each; dependent tasks wait for acceptance.

| ADR | Question | Recommendation |
| --- | --- | --- |
| 0009 | How do large files stay out of git while their hashes stay in manifests? | Git holds text artifacts, manifests, sidecars and logs. Files under `inputs/` other than `*.md`, and everything under `runs/<id>/outputs/`, are ignored by git. Their hashes in manifests and sidecars are the record. `utux init` writes these ignore lines. |
| 0010 | How are stage commits made when the user signs commits? | Commits follow the user's git configuration. Before a run starts, utux makes a test commit in a temporary repository with the same configuration and no terminal. If it fails, `auto` mode refuses to start and `guided` mode warns and continues without commits, recording that in an event. |
| 0011 | How do pauses that are not about an artifact work? | An approval request has a `kind`: `artifact`, `budget_exhausted` or `retry_limit`. Artifact fields are required only for `artifact`. For the other kinds the response is `approve` (continue) or `reject` (stop). Continuing after `budget_exhausted` is accepted only if the budget was raised first, which is a `setting_changed` event. |
| — | Budget (a): a project with a budget and an external provider that reports no cost | Refused unless `budget.allow_unknown_cost` is set to true, which is logged. OpenRouter reports cost, so the default profile is not affected. |
| — | Budget (b): parallel calls | M1 makes one model call at a time per project. A project lock file under `.utux/` makes a second `utux run` on the same project refuse to start. |
| — | Budget (c): reading the whole log before each call | Totals are read once when a run starts and kept in memory, which is safe because of the project lock. |
| — | Sidecar path and current version | The sidecar gains `path`. The current version of a path is the sidecar with the highest version number for it. `utux validate` checks that its `content_hash` matches the file and that every `input_artifacts` entry has a sidecar. |

The four rows without an ADR number are recorded in the documents they
change; they follow from decisions already taken.

Acceptance criteria:
- [x] Three ADRs with status `Proposed`, each with context, decision, alternatives and consequences.
- [x] The maintainer has marked each `Accepted`, or changed it, before M1-03 starts.
- [x] `docs/plan/M0.md` notes that each M1 note was resolved, with a link.

## C. Sandbox executor

### M1-06 Executor contract and conformance suite `[agent]`
Depends on: none.

`Executor` stays internal (ADR-0004) but has a typed contract like the public
interfaces.

- `run(step) -> RunResult`. A step holds: run id, command as a list of arguments, image digest, the project paths to mount read-only, the output directory, resource limits, wall-clock timeout and environment variables.
- `RunResult` holds exit status, start and end time, captured standard output and error (each capped in size), the output files with their hashes, and whether the run was stopped by a limit and which one.
- A scripted executor for tests.

Acceptance criteria:
- [x] The conformance suite runs against the scripted executor.
- [x] The step type refuses environment variables whose names look like credentials (`*KEY*`, `*TOKEN*`, `*SECRET*`, `*PASSWORD*`), with a test.
- [x] Output capture is capped and the cap is reported, not silently cut.

### M1-07 Hardened Docker executor `[agent]`
Depends on: M1-06.

The flags of the specification, section 10, enforced in code and asserted in
tests on the exact `docker run` arguments, plus behaviour tests marked `docker`.

Acceptance criteria:
- [x] Arguments: non-root user, `--read-only`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, the default seccomp profile, `--network=none`, `--pids-limit`, `--memory`, `--cpus`, a size-limited writable tmpfs, no `--privileged`, no `--device` except GPU passthrough when configured, and never the Docker socket or the home directory.
- [x] Mounts: the step's inputs read-only; only the run's output directory writable.
- [x] The wall-clock timeout kills the container and is reported as a limit.
- [x] Docker-marked behaviour tests show, inside the sandbox: writing outside the output directory fails; opening a network connection fails; reading a host path that was not mounted fails; a fork bomb is stopped by the process limit; memory beyond the limit ends the run.
- [x] No environment variable of the host reaches the container unless the step names it.
- [x] If Docker is missing or the daemon is unreachable, the executor fails with a clear message and no fallback to running on the host.
- [x] Rootless Docker is detected and reported in the manifest; it is preferred but not required.

## Retrospective

### What was unclear in M1

- **What an approval covers.** The first rule for the experiment-plan gate
  watched `setting_changed` events; it missed a rebuilt image and a changed
  pack. The rule that held is a record of the execution itself, compared
  before the run (M1-12 review). An approval needs a record of exactly what
  it approves, not a list of things that may have changed.
- **What a rejection does.** It was final in M1-11 and reruns the stage
  with the feedback from M1-13. The plan named the gate but not the answer's
  effect.
- **What "every command refuses an invalid project" means.** Taken
  literally, it blocked `utux approve ... edit`, which needs a file that
  differs from its version, and a crash left a stale lock that `utux unlock`
  could not remove while the log had an incomplete line. Each rule of the
  form "every command" needed its exceptions written out (M1-14 review).
- **When a check is done.** Check 4 was ticked in M1-10 on a test that read
  stage events only; no `code_execution` event existed until M1-15b. The
  criterion named the events; the test did not assert them.
- **Names of stages and nodes, and of runs.** `analysis` is a node of the
  stage `experiment`, and a workflow run (`e-…`) differs from an execution
  run (`r…`). Both needed their own section in `docs/run.md` before
  `--from`, `--to` and the event fields could be stated.
- **What Docker reports.** The memory kill is not always reported
  (`OOMKilled` false after exit 137), and image ids differ between builds of
  the same Dockerfile. Both were found by CI, not by the plan.
- **Defaults.** An unset limit was "not set" in the approval, although the
  executor applied its default; the approval did not name what applied.

### What the first real run found

Nine findings across the maintainer's runs, all about what a real model does
that scripted tests do not: it wraps JSON in a code fence (1), and its raw
answer was lost (2); "the two models" broke a number rule meant for amounts
(3), and the retry did not say why (4); the analyst added a split its record
does not state (5); the methodologist asked for shapes and vague comparisons
(6); the implementer wrote `null`, no tolerance, `train` for cross-
validation and no `random_state` (7); and the shown values and units were
raw (8, 9). Every fix came with a test from a scripted answer shaped like
the real one. The project's total cost was 0.00282495 USD for 12 calls.

### What the M2 plan should state more precisely

- **For every exit check, the test that proves it and what it asserts**:
  the event types, fields or files, not only the behaviour.
- **A real-model run early, not last.** Scripted providers test the code,
  not the prompts; M1's prompts failed on first contact. M2 should plan a
  short real run of each new role before its task is done, by the
  maintainer, with traces kept.
- **Claims about a number's context are verified, not prompted.** Finding 5
  (a split the record does not state) is the first input to the claim
  support verification of RFC-001: what a sentence says about a number's
  metric, model, dataset and split must be checked against the record.
- **The form of every number in prose** as a contract: rounding from the
  tolerance, units, and how a number word is told from an amount.
- **For every rule that applies to "every command" or "every file"**, the
  exceptions and the order of recovery steps.
- **Every new event type with its data keys, its status reasons and its
  `utux validate` rule** in the same task, and which keys older events may
  lack.
- **The image a user runs**: the M5 note on publishing the reference image
  by digest affects reproducing runs on other machines and belongs in the
  plan of the release.

## Notes for later milestones

- **M5 (v1 release): publish the reference image by digest.** The image of
  each pack is built by each user today, and a local build gets a local id
  that differs from the committed `packs/generic/image/digest.txt`
  (`docs/sandbox.md`, "The image digest"). For the release, publish the
  reference image to a registry and record it by digest, so that users pull
  it instead of building it, and runs on other machines use the recorded id.
  This changes what `digest.txt` holds (a registry digest, not a local image
  id) and how the executor checks it, and needs a decision on the registry.
