# RFC-001: Claim Support Verification Protocol

Nov 15, 2026 · @Alan Baghumian

## 1. Summary and scope

This RFC defines how utux Agent decides whether a cited source supports a claim. A claim passes through six steps. Five use language models to varying degrees, with deterministic validation where applicable. The final aggregation step is entirely deterministic, and it alone sets the verdict.

**Status.** Accepted with five amendments after team review on 15 Nov 2026. It refines section 8 of the Technical Product Specification, fixes the implementation contracts for claim support verification, and is the basis for RFC-002.

**Design principles**

- A model may propose; only rules decide. No model output sets a claim's status directly.
- Evidence must be quoted verbatim, and the quote is checked against the stored source text by string matching.
- Every failure path ends in `unverified` or `insufficient_evidence`, never in `verified`.
- `verified` means supported by the evidence that was checked, not proven true.

**In scope.** Claims of type `literature`: statements attributed to one or more cited sources.

**Out of scope.**

- `result` claims, which are covered by numeric traceability against result records.
- `derived` claims, which are valid only if every parent claim is `verified`; checking the inference itself is left to the reviewer agents.
- Whether a reference exists. Citation existence runs before this protocol, and a claim whose source failed that check never enters it.

**What this protocol does not establish.** Verification of evidence support is not verification of scientific truth. The protocol checks whether a source supports the claim as stated. It does not show that the source's result is correct, generalisable or reproducible.

A deterministic final step also does not guarantee a correct verdict. The inputs from S3, S4 and S5 are model outputs and can be wrong, which is why these steps must be scored against the gold-standard set of RFC-002.

## 2. Pipeline at a glance

| Step | Name | Kind | Input | Output |
| --- | --- | --- | --- | --- |
| S1 | Atomic claim extraction | Model, with deterministic validation | A text unit with its citation markers | Atomic claims, each tied to a text span and its cited sources |
| S2 | Evidence localisation | Deterministic retrieval, model selection, deterministic quote check | One claim and its cited sources | Candidate evidence passages with verified verbatim quotes |
| S3 | Semantic agreement | Model | Claim and each evidence passage | One agreement label per claim-passage pair |
| S4 | Scope and conditions | Model slot extraction, deterministic comparison | Claim and supporting passages | Scope flags with severity |
| S5 | Independent assessment | Model from a different family, blind to S3 and S4 | Claim and the source text only | A second agreement label with its own quote |
| S6 | Aggregation and recording | Deterministic | Outputs of S2 to S5 | Status, confidence level, human-review flag, ledger entry |

The pipeline exits early when nothing can be gained from later steps. If S2 finds no usable text or no candidate passage, the claim goes straight to S6 as `insufficient_evidence`.

All model steps run at temperature 0 with structured output validated against a schema. An output that fails validation is retried once, then the step is recorded as failed.

## 3. Step specifications

### S1. Atomic claim extraction

- **Input.** A sentence or paragraph from `literature.md` or the manuscript, its citation keys, and `references.bib`.
- **What it does.** A model splits the text into atomic claims: one assertion each, understandable without the surrounding text, with pronouns resolved. It tags each claim with a kind: `finding`, `quantitative`, `method`, `definition` or `background`.
- **Deterministic checks.** Every claim maps to a character span of the input. Every citation key exists in `references.bib`. No sentence that carries a citation is left without a claim.
- **Output.** `claim_id`, `text`, `span`, `cited_sources`, `kind`.
- **Failure.** A factual claim with no citation is recorded as `insufficient_evidence` with reason `no_source` and returned to the writer.

### S2. Evidence localisation

- **Input.** One claim and the stored text of each cited source in `sources/`.
- **What it does.** The source text is split into passages with stable IDs and character offsets. A hybrid keyword and embedding search returns the top-k passages per source. A model then selects the passages that bear on the claim and returns a verbatim quote from each.
- **Deterministic checks.** Each quote must be an exact substring of the stored passage after whitespace normalisation. A quote that is not found is discarded.
- **Source text provenance.** A matching quote shows that the words are in the stored text. It does not show that the stored text is a faithful copy of the paper. Each source record therefore holds the text hash, the source version (publisher version, preprint version, or abstract from an index), the retrieval route, the extraction method and tool version, and an extraction quality rating.
- **Output.** For each candidate: `source_id`, `passage_id`, `offsets`, `quote`, `checked_text` (`abstract` or `full_text`) and `extraction_quality`.
- **Failure.** No stored text, or no surviving candidate, gives `insufficient_evidence` with reason `no_text` or `no_evidence_found`.

| Extraction quality | Assigned when | Effect |
| --- | --- | --- |
| `clean` | Structured text from an API or publisher XML | None |
| `good` | PDF with a text layer that passes sanity checks | None |
| `degraded` | OCR, or failed sanity checks such as broken columns, missing sections or garbled numbers | Treated like abstract-only evidence: confidence at most `medium`. Quantitative claims go to human review with reason `degraded_source_text` |

### S3. Semantic agreement

- **Input.** The claim and each candidate passage, with one passage of context on either side.
- **What it does.** A model labels each claim-passage pair and names the sentence that justifies the label.
- **Output.** One label per pair, plus a short rationale.

| Label | Meaning |
| --- | --- |
| `entails` | The passage states the claim, or the claim follows from it directly |
| `partial` | The passage supports part of the claim, or a weaker version of it |
| `neutral` | The passage is on the topic but does not settle the claim |
| `contradicts` | The passage states the opposite, or a result that is incompatible with the claim |

The source-level label is the strongest label among its passages, with one exception: if one passage `entails` and another `contradicts`, the source is marked `conflicting` (section 5).

### S4. Scope and conditions

A claim can agree with a passage in wording and still overreach. This step catches the claim that a source makes only for one dataset, one metric or one condition.

- **Input.** The claim and the passages labelled `entails` or `partial`.
- **What it does.** A model fills the same slot template for the claim and for the evidence: population or dataset, method or intervention, comparator, outcome or metric, direction, magnitude, conditions, certainty wording, and study type. A deterministic comparator then compares the two filled templates slot by slot.
- **Output.** A list of scope flags.

| Flag | Raised when | Severity |
| --- | --- | --- |
| `direction_mismatch` | The claim and the evidence point in opposite directions | Critical |
| `causal_overreach` | The claim is causal and the evidence is correlational or observational | Critical |
| `magnitude_mismatch` | Numbers differ beyond rounding, or relative and absolute change are confused | Critical |
| `overgeneralisation` | The claim's population, dataset or conditions are broader than the evidence | Major |
| `metric_mismatch` | The claim names a different outcome or metric from the evidence | Major |
| `certainty_escalation` | Hedged evidence, such as "suggests", is stated as established fact | Minor |
| `missing_comparator` | The claim drops the baseline that the evidence compares against | Minor |

Numbers in the magnitude slot are compared by code, not by the model.

### S5. Independent assessment

- **Input.** The claim and the top-k retrieved passages for each source. It does not receive the quotes, labels, rationales or flags from S2 to S4.
- **What it does.** A model from a different family than the S3 model gives its own source-level label, using the same four labels, and its own verbatim quote.
- **Deterministic checks.** The quote check of S2 is applied again.
- **Output.** A label and a verified quote per source.
- **Failure.** If the second model is unavailable, the claim cannot become `verified`; it is recorded as `unverified` with reason `second_assessor_unavailable`.

### S6. Aggregation and recording

A deterministic function applies the rules of sections 4 and 5 to the outputs of S2 to S5, sets the status, the confidence level and the human-review flag, and writes the ledger entry and the trace (section 6). No model is called.

## 4. Decision rules

Rules are applied per cited source first, then combined across sources (section 5).

### Order of evaluation

S6 applies the rules in this fixed order for each source. The first rule that matches ends the evaluation for that source.

1. **Step failures.** `no_source`, `no_text`, `no_evidence_found` or `second_assessor_unavailable` give the status stated in section 3.
2. **Conflict within the source.** If one passage `entails` and another `contradicts`, the status is `insufficient_evidence`, `needs_human` is true and the reason is `conflict_within_source`. This rule takes precedence over the agreement matrix.
3. **Critical scope flag.** The status is `insufficient_evidence`, `needs_human` is true and the flag is recorded in `reasons`.
4. **Agreement matrix.** The two assessments are combined by the table below.
5. **Major and minor scope flags.** The matrix result is adjusted.
6. **Confidence level.** Set from the final status.

Source-level results are then combined across sources by the rules of section 5.

### Source-level status from the two assessments

Rows are the primary label from S3; columns are the independent label from S5.

| S3 \\ S5 | `entails` | `partial` | `neutral` | `contradicts` |
| --- | --- | --- | --- | --- |
| `entails` | `verified` | `partially_supported` | `insufficient_evidence` | `insufficient_evidence`, human review |
| `partial` | `partially_supported` | `partially_supported` | `insufficient_evidence` | `insufficient_evidence`, human review |
| `neutral` | `insufficient_evidence` | `insufficient_evidence` | `insufficient_evidence` | `insufficient_evidence`, human review |
| `contradicts` | `insufficient_evidence`, human review | `insufficient_evidence`, human review | `insufficient_evidence`, human review | `contradicted` |

A claim is rejected automatically only when both assessors independently find a contradiction with verified quotes. A single contradiction always goes to a human.

### Adjustment for scope flags

| Highest flag severity | Effect |
| --- | --- |
| None | No change |
| Minor | No change to the status; the flag is shown to the writer as a suggested rewording, and confidence is at most `medium` |
| Major | `verified` is downgraded to `partially_supported` |
| Critical | The status is `insufficient_evidence` until a human has reviewed the claim, whatever the matrix would give. The flag is recorded in `reasons`, so the entry shows a serious mismatch between claim and evidence and not a lack of evidence |

Scope flags never upgrade a status. A critical flag does not produce `contradicted` automatically, because the flag rests on one model's slot extraction; the human reviewer decides.

### Confidence level

Confidence expresses how strongly the checked evidence supports the claim. It is not confidence in the correctness of the classification, so two assessors who agree on `contradicts` do not produce `high`. It is an ordinal level set by rule, not a model-reported probability.

| Level | Conditions |
| --- | --- |
| `high` | The status is `verified`, both assessors label `entails`, there is no scope flag, and the evidence is full text of `clean` or `good` extraction quality |
| `medium` | The status is `verified`, and the evidence is abstract-only or `degraded`, or a minor flag is present |
| `low` | Every other status |

Confidence in the classification decision itself may be defined separately later, once gold-set results exist.

### What happens to each status

| Status | Use in the manuscript |
| --- | --- |
| `verified` | Allowed |
| `partially_supported` | Returned to the writer with the flags; the claim must be narrowed to what the evidence supports and re-checked, or accepted by the user at a gate |
| `contradicted` | Blocked; the writer must remove or reverse the claim |
| `insufficient_evidence` | Blocked unless the user accepts it at a gate; the writer may look for another source |
| `unverified` | Blocked until the check has run |

### Human review triggers

- The two assessors disagree and one of them says `contradicts`.
- A critical scope flag is raised.
- Cited sources conflict with each other (section 5).
- The claim appears in the abstract or the conclusions and its confidence is not `high`.
- A random audit sample of `verified` claims, 5% by default, to measure the false-positive rate in use.

The human sees the claim, the quotes in context and both assessments, and sets the final status. The entry records `verified_by: human:<id>` and keeps the machine verdict beside it.

## 5. Conflicting evidence

Conflict is never resolved by majority vote or by a model choosing a side. It is recorded and shown to a human.

| Situation | Rule |
| --- | --- |
| One source: one passage `entails`, another `contradicts` | The source is `conflicting`. Status is `insufficient_evidence` with flag `conflict_within_source`, and the claim goes to human review. Typical cause: a result that holds in one experiment or subgroup and fails in another |
| Several cited sources, all support | Claim status is the weakest of the supporting source statuses |
| Several cited sources, some support and some are `neutral` or `insufficient_evidence` | Claim status follows the supporting sources. Each non-supporting citation is flagged `citation_not_supporting` and removed from that claim by the writer |
| Several cited sources, at least one supports and at least one is `contradicted` | Status is `insufficient_evidence` with flag `conflict_across_sources`, and the claim goes to human review. The writer is asked to rewrite it as a statement that the evidence is mixed, citing both sides |
| A source that was not cited contradicts the claim | Out of scope for this protocol. Searching for contrary evidence belongs to the literature stage and the reviewer rubric |

A rewritten claim, such as one that reports mixed evidence, is a new claim and passes through the protocol again.

## 6. Claim ledger record

The ledger line in `claims.jsonl` holds the verdict and enough to audit it at a glance. The full step-by-step trace is stored once per check in `verification/<claim_id>/<check_id>.json` and referenced from the ledger.

```json
{"id": "C031", "type": "literature", "kind": "finding",
 "text": "Method A outperforms method B on image classification.",
 "span": {"file": "literature.md", "start": 2140, "end": 2198},
 "status": "partially_supported", "confidence": "low", "needs_human": false,
 "reasons": ["overgeneralisation"],
 "evidence": [{
   "source_id": "doi:10.0000/example", "passage_id": "p014", "offsets": [5321, 5467],
   "quote": "A exceeded B by 1.8 points on dataset X",
   "checked_text": "abstract",
   "primary_label": "entails", "secondary_label": "entails",
   "scope_flags": [{"flag": "overgeneralisation", "severity": "major",
                    "claim_slot": "image classification", "evidence_slot": "dataset X"}]}],
 "verified_by": ["support_check@1"],
 "check_id": "k-000218", "trace": "verification/C031/k-000218.json",
 "claim_hash": "sha256:...", "checked_at": "2026-11-15T11:02:40Z",
 "human": null}
```

| Field | Purpose |
| --- | --- |
| `status`, `confidence`, `needs_human` | The verdict from S6 |
| `reasons` | Machine-readable causes: scope flags, `no_source`, `no_text`, `no_evidence_found`, `assessor_disagreement`, `conflict_within_source`, `conflict_across_sources`, `second_assessor_unavailable` |
| `evidence[]` | One entry per cited source: the verified quote, where it sits, which text was checked, both labels and the flags |
| `verified_by` | The check and its protocol version, or `human:<id>` |
| `trace` | Path to the full record: prompts by version, model IDs, raw outputs, filled slot templates, retrieval results |
| `claim_hash` | Hash of the claim text and its source IDs, used to detect that a re-check is needed |
| `human` | When reviewed: reviewer ID, decision, note and time. The machine verdict is kept |

The example in section 7 of the specification used a numeric `confidence`. This RFC replaces it with the ordinal level for literature claims. Each check also emits a `verification_result` event to `events.jsonl`.

Each evidence entry also carries `extraction_quality`, and `degraded_source_text` joins the list of reasons.

## 7. Safeguards, cost control and re-verification

### Safeguards

- **Fabricated evidence.** Every quote is matched against the stored source text by code. A model cannot invent a passage.
- **Instructions inside sources.** Source text is passed as data in a delimited block. Assessor prompts state that text inside it is never an instruction, and structured output limits what a manipulated model can return.
- **Shared blind spots.** S5 uses a different model family and sees none of the earlier outputs. This lowers correlated errors but does not remove them; the gold set measures what remains.
- **Abstract-only evidence.** A claim checked against an abstract can be `verified`, but its confidence is at most `medium` and `checked_text` records the limit.
- **Failures.** A timeout, an invalid output or an unavailable model leaves the claim `unverified` with a reason. Nothing defaults to `verified`.

### Cost control

- Early exit after S2 when there is no text or no candidate passage.
- S4 runs only on passages labelled `entails` or `partial`.
- S1 and S2 selection use the `light` or `standard` tier. S3 and S5 use the models chosen by the reviewer-role benchmark.
- Results are cached by `claim_hash`, source text hash, prompt versions and model IDs. An unchanged claim is never checked twice.
- Claims that cite the same source share its passage index and retrieval results.

### Re-verification triggers

A stored verdict is discarded and the claim returns to `unverified` when any of these change: the claim text, its cited sources, the stored source text, the protocol version, or the prompt version of any model step. A change of model ID alone does not discard verdicts, but it is logged and the gold-set scores are re-run for the new model.

## 8. Accepted defaults and what this fixes for the gold set

### Accepted defaults

The team accepted these six defaults on 15 Nov 2026. They are working values, not proven ones, and are tuned with benchmark results.

| Question | Accepted default |
| --- | --- |
| How many passages does retrieval return per source? | k = 8 for full text; all passages for an abstract |
| Ordinal confidence or a calibrated probability? | Ordinal in v1 |
| What share of `verified` claims is audited by a human? | 5%, configurable per project |
| Are claims in the abstract and conclusions always reviewed by a human? | Only when confidence is below `high` |
| Does S5 run when S3 returns `neutral` for every passage? | Yes |
| Is the list of seven scope flags complete? | Sufficient for v1; extended only when benchmark errors show a recurring pattern |

The value of k and the audit share must be examined empirically. A 5% audit is an operational check and may be too small to estimate an error rate, especially when few claims are `verified`. The evaluation in RFC-002 therefore runs on the complete, independent gold-standard set and never on a 5% sample.

### What this protocol fixes for the gold-standard set

The gold set (RFC-002) must be able to score every step separately, as well as the final verdict. This protocol fixes the labels it needs.

| Protocol output | Gold annotation needed | Scored with |
| --- | --- | --- |
| S1 atomic claims | Reference list of atomic claims per text unit | Precision and recall of extracted claims |
| S2 evidence passages | Reference evidence spans per claim and source | Recall of the reference span in the top-k; quote accuracy |
| S3 and S5 labels | One of the four agreement labels per claim-source pair | Per-label precision, recall and F1; agreement between assessors |
| S4 scope flags | The set of flags that apply, from the seven above | Per-flag precision and recall |
| S6 status | One of the four scientific statuses per claim; unverified is an operational state and is reported as a failure rate | Per-status precision, recall and F1; false-positive rate of `verified` |
| Human-review flag | Whether an expert would want to see the claim | Share of true errors caught by the flag; review load |

The measure that matters most is the false-verified rate: the share of claims marked `verified` whose reference status is not `verified`. RFC-002 defines it and its interval.

### Principles carried into RFC-002

Reference labels are never produced by running utux Agent and then accepted as ground truth without independent review. The labelling process is:

1. Select claims and sources.
2. Two human annotators label independently.
3. Record every disagreement.
4. Resolve disagreements through a third annotator or joint adjudication.
5. Freeze a version of the reference set.
6. Evaluate utux Agent without changing the reference labels.

The set must include hard cases, because they are what test S4 and S5. Two examples: a claim that agrees with the abstract while the full text narrows it, and a claim with the correct number attached to the wrong dataset.
