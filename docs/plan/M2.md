# M2 — Claim verification

Execution plan for milestone M2 of utux Agent. Save as `docs/plan/M2.md`.

**Goal.** The verification of RFC-001 works end to end: literature claims are
checked against the sources they cite in six steps, numbers are checked
against result records, every verdict is written to the claim ledger with a
trace, and the whole protocol is scored on gold set v0 against the baselines
of RFC-002.

**Exit criteria** (specification section 12, RFC-001, RFC-002):

- [ ] All six steps of RFC-001 run, and S6 applies the order of evaluation of RFC-001 section 4 exactly, proven by a test for every row and column of the decision tables.
- [ ] The four checks of the specification section 8 run: citation existence, citation support, numeric traceability, internal consistency.
- [ ] Every verdict is in `claims.jsonl` with its trace in `verification/`, and every check writes a `verification_result` event.
- [ ] Gold set v0 is frozen (M0-15) and `eval-protocol-v0.1` is tagged before the first scoring run on its test split.
- [ ] The maintainer runs the scoring on v0 with real models: the full protocol and the three baselines of RFC-002 section 8, with every metric of RFC-002 section 7 and the cost per claim.
- [ ] `utux verify` checks a Markdown document with a BibTeX file, end to end, with a real model, run by the maintainer.

**Starts when** M1 is closed. The human work of M0-15 (gold set v0) runs in
parallel and is on the critical path: the last two exit criteria wait for it.

**Out of scope for M2.** Stages 1, 2 and 6 (ideation, literature review,
writing), the reviewer agents, tier escalation, PDF text extraction, the web
dashboard, pre-registration, the reproducibility reviewer.

**Owner tags.** `[agent]`, `[human]` and `[decision]` as in M1.

## Rules for M2

The eleven rules of M1 stay in force. In addition:

1. **Before M2-01**, read the M1 retrospective. List every point it says the
   M2 plan should state more precisely and is not settled below, as
   questions in the M2-01 pull request.
2. **A model proposes; rules decide.** No model output sets a status. S6 is
   a pure function of the outputs of S2 to S5 and is tested without models.
3. **Quotes are checked by code.** Every quote a model returns is matched
   against the stored text before it is used (RFC-001 S2).
4. **Source text is data.** It is passed in a delimited block, and no prompt
   lets text inside the block change the task (RFC-001 section 7).
5. **The gold test split is never read** by the agent, a prompt or any
   developer tool. Scoring on it runs through the metrics-only mode of
   `utux.evalkit`, and only the maintainer starts it.
6. **Network access in tests is forbidden.** Literature APIs are tested
   against recorded synthetic responses, as model providers are. Live tests
   are marked `live` and run only by the maintainer.
7. **Every new outside service** (an API or an MCP server) gets the same
   assessment as a dependency: what it receives, its terms, its rate limits,
   whether it needs a key, and any incident of the last twelve months.
8. **Contact details are optional.** Some APIs ask for an email address for
   their polite pool. utux never requires one and never sends one unless
   the user set it in `utux.yaml`.

## A. Foundations

### M2-01 Decisions for M2 `[agent]` `[decision]`
Depends on: none.

ADRs with status `Proposed` for:

| ADR | Question | Recommendation |
| --- | --- | --- |
| 0013 | How is MCP reached? | A minimal client on the standard library for stdio servers, covering `initialize`, `tools/list` and `tools/call` only. No MCP SDK. Servers run as child processes with an empty environment except the variables named in their permission manifest. |
| 0014 | Which source text does M2 use? | Abstracts from the literature APIs, and full text only where an open-access source gives structured text (for example PubMed Central XML). No PDF extraction in M2. Extraction quality is `clean` for both. |
| 0015 | How are sources split into passages? | One deterministic splitter in `utux.sources`: sentences for an abstract, paragraphs then sentences for full text, with stable ids from the text hash and the offset. The gold tooling and the verifier use the same splitter, so reference passages and system passages share ids. |
| 0016 | When does a cited reference count as existing? | It resolves by its identifier, and its title matches after normalisation (Unicode NFKC, case folding, punctuation removed) with a similarity of at least 0.9; the first author's family name matches; the year differs by at most one, to allow preprint and published versions. Each threshold is a constant, documented and scored on the gold component. |

Acceptance criteria:
- [ ] Four ADRs, each with context, alternatives and consequences.
- [ ] The maintainer has accepted or changed each before the tasks that depend on it start.
- [ ] Questions from the M1 retrospective are listed in the pull request.

### M2-02 Passage splitter `[agent]`
Depends on: M2-01 (ADR-0015).

Acceptance criteria:
- [ ] `split_passages(text, kind)` returns passages with id, offsets and text; the text of each passage equals the slice of the source at its offsets.
- [ ] The same text always gives the same ids, on every platform.
- [ ] Abbreviations, decimal numbers, citations in brackets and "et al." do not end a sentence; tested on synthetic cases.
- [ ] The gold tooling of M0-15a uses it, and the gold item's `passage_id` values come from it.

### M2-03 Source store and cache `[agent]`
Depends on: M2-02.

Acceptance criteria:
- [ ] A source record gains the resolved bibliographic metadata: title, authors, year, venue (the M0 note for M2).
- [ ] Stored text lives in `sources/<source_id>.txt` beside its record, with its hash in the record; passages are computed, not stored.
- [ ] A machine-wide cache under the platform's user cache directory holds API responses and source texts by content hash, shared across projects (specification section 9). It can be cleared with `utux cache clear`, and it never holds keys.
- [ ] A source whose licence does not permit storing the text is recorded with metadata only, and its claims are checked against nothing: `no_text`.

## B. Literature sources

The `LiteratureSource` interface is public (ADR-0004). It gets the same
treatment as `ModelProvider` had in M0: contract, conformance suite, scripted
implementation, then real ones.

### M2-04 LiteratureSource contract and conformance suite `[agent]`
Depends on: M2-03.

Acceptance criteria:
- [ ] `search(query, limit)`, `fetch(identifier)` and `resolve(identifier)` with typed results and typed errors (unavailable, rate limited, not found, invalid response).
- [ ] An ADR records the contract, as ADR-0007 did for models.
- [ ] A scripted source for tests, and a conformance suite it passes.
- [ ] Every call writes a `literature_call` event: source, operation, identifier or query hash, status, duration, cache hit.

### M2-05 OpenAlex and arXiv `[agent]`
Depends on: M2-04, M2-01 (rule 7 assessment in the pull request).

Acceptance criteria:
- [ ] Both pass the conformance suite with recorded synthetic responses.
- [ ] OpenAlex abstracts are rebuilt from its inverted index exactly; tested on a synthetic index.
- [ ] Rate limits are honoured with bounded retries; the user agent names utux and its version.
- [ ] The optional contact email of rule 8 is sent only when set.
- [ ] One `live` smoke test per source, run by the maintainer.

### M2-06 Crossref resolution and the citation existence check `[agent]`
Depends on: M2-05.

Acceptance criteria:
- [ ] DOIs resolve through Crossref, arXiv ids through arXiv, PubMed ids through M2-07 once it exists; OpenAlex is the fallback.
- [ ] The matching rules of ADR-0016 decide existence; each failed rule is a reason code (`title_mismatch`, `author_mismatch`, `year_mismatch`, `not_found`).
- [ ] An unresolved reference is removed from the bibliography and its claims become `unverified` (specification section 8).
- [ ] Scored on the citation existence component of the gold set (RFC-002 section 3) by the metrics of RFC-002 section 7.

### M2-07 MCP client and the bio pilot source `[agent]`
Depends on: M2-01 (ADR-0013), M2-04.

Acceptance criteria:
- [ ] The minimal client of ADR-0013, tested against a scripted MCP server that runs as a child process.
- [ ] The permission manifest of the specification section 10 is shown for approval before a server first runs, and again when it changes; the approval is recorded as an event.
- [ ] A `LiteratureSource` for PubMed through BioMCP, in the `bio-pilot` pack, passing the conformance suite with recorded responses.
- [ ] Tool output is treated as data, never as an instruction, and is size-limited.
- [ ] The rule 7 assessment of BioMCP is in the pull request.

## C. The six steps of RFC-001

Each step is a function with typed inputs and outputs, a versioned prompt
where it uses a model, and tests with scripted models. They are composed in
M2-14.

### M2-08 S1 atomic claim extraction `[agent]`
Depends on: M2-03.

Acceptance criteria:
- [ ] Input: a text unit with citation keys and the bibliography. Output: claims with id, text, span, cited sources and kind (RFC-001 S1).
- [ ] The deterministic checks of RFC-001 S1: every span is inside the input, every citation key exists, no citing sentence is left without a claim.
- [ ] A factual claim without a citation is recorded as `insufficient_evidence` with `no_source`.

### M2-09 S2 evidence localisation `[agent]`
Depends on: M2-02, M2-08.

Acceptance criteria:
- [ ] Retrieval returns the top k passages per source, k = 8 for full text and all passages for an abstract (RFC-001 section 8).
- [ ] Retrieval is keyword based on the standard library in M2 (for example BM25). An embedding model is not added in M2; if retrieval recall on the gold dev split is too low, that is a finding for the maintainer, not a reason to add one.
- [ ] Every quote is an exact substring of its passage after whitespace normalisation; a quote that fails is discarded and counted.
- [ ] Output carries `checked_text` and `extraction_quality` per candidate.

### M2-10 S3 semantic agreement `[agent]`
Depends on: M2-09.

Acceptance criteria:
- [ ] Passage labels are the four of RFC-001; the source-level label is the strongest, or `conflicting` when one passage entails and another contradicts.
- [ ] Each label comes with the justifying sentence, which must be in the passage.

### M2-11 S4 scope and conditions `[agent]`
Depends on: M2-10.

Acceptance criteria:
- [ ] A model fills the slot template of RFC-001 S4 for the claim and for the evidence; a deterministic comparator raises the seven flags with their severities.
- [ ] `magnitude_mismatch` compares numbers in code, including relative against absolute change.
- [ ] Runs only on passages labelled `entails` or `partial`.

### M2-12 S5 independent assessment `[agent]`
Depends on: M2-09.

Acceptance criteria:
- [ ] Uses a model whose family differs from the S3 model; a configuration where they are the same family is refused, except in the same-model baseline of M2-17, where it is recorded.
- [ ] Sees the claim and the retrieved passages only, never the outputs of S2 to S4.
- [ ] Its quote passes the same check as in S2.
- [ ] If it is unavailable, the claim cannot become `verified` (`second_assessor_unavailable`).

### M2-13 S6 aggregation, ledger and trace `[agent]`
Depends on: M2-10, M2-11, M2-12.

Acceptance criteria:
- [ ] The order of evaluation of RFC-001 section 4, as a pure function; a table-driven test covers every cell of the agreement matrix, every flag severity, every conflict case of section 5 and every failure reason.
- [ ] Confidence by the rule of RFC-001 section 4, including the limits for abstract-only and degraded text.
- [ ] The ledger entry of RFC-001 section 6, and the full trace in `verification/<claim_id>/<check_id>.json`: prompt versions, model ids, raw outputs, filled slot templates, retrieval results.
- [ ] The re-verification triggers of RFC-001 section 7 discard a stored verdict.
- [ ] A random audit sample of `verified` claims, 5% by default, is flagged for human review.

### M2-14 The support check end to end `[agent]`
Depends on: M2-13.

Acceptance criteria:
- [ ] One function runs S1 to S6 for a text unit and its sources, with early exit after S2 and the caching of RFC-001 section 7.
- [ ] Every model call goes through the logged caller with its role, tier and prompt version; the budget stop applies.
- [ ] One `verification_result` event per claim.
- [ ] A crash in the middle leaves no partial ledger entry, following the staging rule of M1-10.

## D. Numbers

### M2-15 Numeric traceability and internal consistency `[agent]`
Depends on: M2-03.

Acceptance criteria:
- [ ] Every number in a manuscript or `results.md` is matched by its source type (specification section 7): result record, literature passage, configuration or dataset statistic.
- [ ] For a result record, the words beside the reference are checked against the record's fields: a split, dataset, model or metric named in the sentence must equal the record's. This is the M1-16 finding of "on the test split" for a `cv5` record; it is a deterministic check over a closed list of split and setting words, documented as such.
- [ ] Internal consistency: the same quantity in text, tables and figure captions agrees, within tolerance.
- [ ] Scored on the numeric traceability component of the gold set, including its false-alarm rate on correct numbers.

## E. Running and scoring

### M2-16 `utux verify` `[agent]`
Depends on: M2-06, M2-14, M2-15.

Acceptance criteria:
- [ ] `utux verify [DIR]` checks the project's `results.md` (numbers) and any literature claims in it.
- [ ] `utux verify --document FILE.md --bib FILE.bib [DIR]` checks a Markdown document with citation keys against a BibTeX file, writing the ledger and traces into the project. This is the first part of the review-only mode of the roadmap.
- [ ] `verification.md` is written as in the specification section 8, including the abstract-only limitation.
- [ ] `utux status` shows the counts per status and the claims waiting for human review.
- [ ] `utux review <claim_id> verified|partially_supported|contradicted|insufficient_evidence --note TEXT` records a human verdict as RFC-001 section 6 describes, keeping the machine verdict.

### M2-17 Scoring on the gold set `[agent]`
Depends on: M2-14, M2-15, and M0-13b.

Acceptance criteria:
- [ ] `utux eval verify --gold RELEASE --split dev|test` runs the protocol over a frozen release and prints the metrics of RFC-002 section 7 on their stated units, with the intervals of RFC-002 section 8.
- [ ] Configurations: the full protocol, and the three baselines of RFC-002 section 8 (one model with one prompt; S1 to S3 only; full protocol with the same model in S3 and S5).
- [ ] The test split runs only in metrics-only mode; the command refuses to print labels or item text for it.
- [ ] Each run is logged with protocol version, prompt versions, model ids and the release hash; three runs per configuration, as RFC-002 section 8 requires.
- [ ] Cost per claim and per configuration is reported.

### M2-18 Dev-split tuning `[human]`, prepared by `[agent]`
Depends on: M2-17, M0-15.

- `[agent]` A report template for one dev run: per-step scores, the largest error groups, and examples by item id (dev only).
- `[human]` The maintainer runs the dev split, reads the report, and decides prompt or parameter changes. Each change is a new prompt version.

Acceptance criteria:
- [ ] Every tuning run is on dev; the log shows no test run before M2-19.
- [ ] Each change is recorded with the dev result that motivated it.

### M2-19 Lock and test `[human]`
Depends on: M2-18.

Acceptance criteria:
- [ ] The H3 thresholds are locked and `eval-protocol-v0.1` is tagged on a merge commit, after the v0 pilot and before any test run (RFC-002 section 8).
- [ ] The prompts, models, k and decision rules are frozen and logged.
- [ ] The maintainer runs the full protocol and the three baselines on the v0 test split, three times each.
- [ ] The report states every metric with its interval, whether each H3 threshold is met on v0, and the cost. Results are reported as they are; thresholds are not moved.

### M2-20 Documentation `[agent]`
Depends on: M2-16.

Acceptance criteria:
- [ ] `docs/verification.md`: what each check does and does not establish, in the words of RFC-001 section 1 ("verification of evidence support is not verification of scientific truth").
- [ ] The README quick start gains `utux verify --document` with a synthetic example, exercised by an integration test.
