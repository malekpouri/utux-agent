# RFC-002: Gold Standard Dataset and Evaluation Protocol

Nov 15, 2026 · @Alan Baghumian

## 1. Summary, scope and principles

This RFC defines the gold-standard set that utux Agent's verification is scored against, how its reference labels are made, and how each metric is computed. The set is built and frozen by people, independently of the system, before any result is reported.

**Status.** Accepted with revisions after team review on 15 Nov 2026. It builds on RFC-001 and uses its labels: four agreement labels, seven scope flags, four scientific claim statuses and the human-review flag. `unverified` is an operational state of the system, not a reference label (section 3).

**Scope.** The main part covers claim support verification (RFC-001). Section 3 also lists the three smaller components that the Technical Product Specification requires: citation existence, numeric traceability and methodological errors.

**Principles**

1. Reference labels are never produced by running utux Agent and then accepted as ground truth without independent human review.
2. Annotators label from the claim and the source text only. They do not see system output, each other's labels, or how an item was constructed.
3. The set, the annotation guideline and the metric definitions are frozen and versioned before evaluation. Labels are not changed in response to system results.
4. Evaluation runs on the complete set, never on a sample.
5. The set measures whether a source supports a claim. It does not measure whether the source's finding is true.

## 2. Sources of items and kinds of claims

Items come from three sources. Each has a different job, and no single one is enough.

| Source | How items are made | Why it is needed | Weakness |
| --- | --- | --- | --- |
| Natural claims | Citing sentences taken from published open-access papers, paired with the paper they cite | Real scientific writing with real citation practice | Mostly supported claims; few errors |
| Controlled perturbations | A person rewrites a supported natural claim to introduce exactly one defined error, or attaches it to the wrong source | Guarantees enough examples of every error type, including rare and hard ones | Less natural than real mistakes |
| System-generated claims | Claims sampled from real runs of utux Agent and of the baselines, then labelled by people | Reflects the errors agents actually make | Distribution shifts as the system changes |

Only sources whose licence allows storing the text are used: open-access papers in machine learning and in biomedicine, the two v1 domains. Each source record holds:

- DOI or other identifier, and the original URL.
- Licence, and whether it permits redistribution of the full text, of the abstract, or of neither.
- Retrieval date, text hash and extraction method.

Where a licence does not permit redistribution, the public release carries only the identifier, metadata, labels and evidence offsets, and only if that is itself compatible with the source's terms.

Existing public datasets for scientific claim verification, such as SciFact, serve as a secondary, external check of how well the protocol generalises. They do not replace the main evaluation and their labels are not merged into this set, because their label definitions differ from RFC-001.

### Perturbation types

Each perturbation targets one check in RFC-001. One edit can cause more than one error: changing a number can produce both `magnitude_mismatch` and a contradiction. Three things are therefore stored for every perturbed item, hidden from annotators, who label the item blind:

1. The target error.
2. Any secondary errors the author of the perturbation expects.
3. A human confirmation, made after blind annotation, of whether only the target error is present.

An item confirmed to contain only its target error is tagged `single_error`. Every other perturbed item is tagged `multi_error`. Per-check analysis of S3 and S4 uses `single_error` items; overall metrics use both.

| Perturbation | Expected gold label | Tests |
| --- | --- | --- |
| Reverse the direction of the effect | `contradicted`, flag `direction_mismatch` | S3, S4 |
| Turn a correlation into a causal statement | Flag `causal_overreach` | S4 |
| Change the number, or swap relative and absolute change | Flag `magnitude_mismatch` | S4 |
| Widen the population, dataset or conditions | `partially_supported`, flag `overgeneralisation` | S4 |
| Swap the metric or outcome | Flag `metric_mismatch` | S4 |
| Remove the hedge | Flag `certainty_escalation` | S4 |
| Drop the comparator | Flag `missing_comparator` | S4 |
| Attach the claim to an unrelated paper on the same topic | `insufficient_evidence` | S2, S3 |
| Attach the claim to a paper that reports the opposite | `contradicted` | S3, S5 |

### Kinds of claims

The set covers all five claim kinds of RFC-001: `finding`, `quantitative`, `method`, `definition` and `background`. Findings and quantitative claims are over-represented on purpose, because they carry the most risk.

## 3. Composition and size

All sizes in this section are proposals for the team to confirm.

### Two releases

| Release | Size | Used for | Needed by |
| --- | --- | --- | --- |
| v0 pilot | About 150 claims | Calibrating the guideline, first scoring of the verification checks | M0 to M2 |
| v1 | About 600 claims, and more pairs, since some claims cite several sources | The benchmark and the paper | M4 |

### Strata for v1

The set is stratified so that every label has enough items to be scored on its own.

Reference labels use four scientific statuses: `verified`, `partially_supported`, `contradicted` and `insufficient_evidence`. `unverified` means the system has not completed a check, for example after a timeout or a model outage. It never appears as a reference label, and it is reported separately as a failure rate (section 7).

| Dimension | Target |
| --- | --- |
| Gold status | About 240 `verified`, 150 `contradicted`, 110 `partially_supported` and 100 `insufficient_evidence` |
| Scope flag | At least 30 claim-source pairs for each of the seven flags |
| Domain | About 60% machine learning, 40% biomedicine |
| Evidence text | About half abstract-only, half full text |
| Item source | About 40% natural, 40% perturbed, 20% system-generated |
| Multi-source claims | At least 60 claims that cite two or more sources, including 20 with conflicting sources |

### Why the statuses are not equal in size

The sizes follow the two error rates that must be shown to be small, not an equal split.

- **False-verified rate.** Its denominator is the number of claims the system marks `verified`, which is known only after a run. With about 240 reference-`verified` claims and coverage near 80%, roughly 200 claims are system-verified. If 5% of 200 are wrong, the 95% interval reaches to about 9%, just inside the 10% bound. With 120 system-verified claims the same rate gives an upper end above 10%.
- **Critical miss rate.** Its denominator is the number of reference-`contradicted` claims. With no misses at all, the 95% upper bound is roughly 3 divided by the number of items, so 150 items are needed before a bound of 2% can be shown.

These are approximate planning figures. The v0 pilot provides first estimates of coverage and error rates, and the sizes are then confirmed by a formal sample-size calculation before v1 annotation starts. Zero observed errors never supports a claim that the error rate is zero.

### Hard cases

Hard cases are collected deliberately, because they are what separate a careful checker from a superficial one. At least 100 items in v1 fall into one of these groups:

- The claim agrees with the abstract, but the full text narrows or qualifies it (`abstract_vs_full_text`).
- The number is correct but is attached to the wrong dataset, metric or split (`number_wrong_context`).
- The source supports the claim in one experiment and contradicts it in another (`conflict_within_source`).
- The claim is true in general but is not stated in the cited source (`true_but_not_in_source`).
- The source states the claim only as prior work by others, not as its own finding (`attributed_prior_work`).
- The claim paraphrases the source so heavily that keyword search fails to find the evidence (`heavy_paraphrase`).
- A negated or hedged sentence in the source is easy to read as support (`negation_or_hedge`).

The code in brackets is the value of an item's `hard_case` field (section 4); an item outside these groups has `hard_case` null.

### Other components of the gold set

These three components have labels that are known by construction. A second person still checks every item.

| Component | Items | Reference label |
| --- | --- | --- |
| Citation existence | Real references, invented references, and real references with altered title, authors or year | Known by construction; real ones confirmed against the publisher record |
| Numeric traceability | Manuscript excerpts with their result records, some with a wrong value, or a right value under the wrong metric, dataset, model or split | Known by construction |
| Methodological errors | Short experiment designs and code with planted faults, such as test-set leakage, tuning on the test set, or a missing baseline, mixed with sound ones | Planted by an expert and confirmed by a second expert |

## 4. Item schema

One gold item is one text unit with its claims, sources and reference labels. It carries a reference answer for every step of RFC-001, so each step can be scored separately.

```json
{"schema_version": 1, "item_id": "G0412", "gold_version": "1.0", "split": "test", "domain": "ml",
 "origin": "perturbed", "hard_case": "abstract_vs_full_text",
 "text_unit": "Method A outperforms method B on image classification [12].",
 "claims": [{
   "claim_id": "G0412-c1", "text": "Method A outperforms method B on image classification.",
   "span": [0, 53], "kind": "finding",
   "pairs": [{
     "pair_id": "G0412-c1-s1", "source_id": "doi:10.0000/example", "source_group": "sg-0087",
     "text_hash": "sha256:...", "checked_text": "full_text", "extraction_quality": "good",
     "evidence_spans": [{"passage_id": "p014", "offsets": [5321, 5467]}],
     "agreement_label": "partial",
     "scope_flags": ["overgeneralisation"],
     "raw": {"a03": {"evidence_spans": [{"passage_id": "p014", "offsets": [5321, 5467]}],
                     "agreement_label": "partial", "scope_flags": ["overgeneralisation"]},
             "a07": {"evidence_spans": [{"passage_id": "p014", "offsets": [5321, 5467]}],
                     "agreement_label": "entails", "scope_flags": []}},
     "adjudicated": true}],
   "status": "partially_supported",
   "expert_would_review": false,
   "raw": {"a03": {"status": "partially_supported", "expert_would_review": false},
           "a07": {"status": "partially_supported", "expert_would_review": false}},
   "adjudicated": false,
   "ambiguous": false}],
 "annotation": {"annotators": ["a03", "a07"], "adjudicator": "a01",
                "claim_extraction": {
                  "raw": {"a03": [{"span": [0, 53], "text": "Method A outperforms method B on image classification."}],
                          "a07": [{"span": [0, 53], "text": "Method A outperforms method B on image classification."}]},
                  "adjudicated": false}},
 "hidden": {"target_error": "overgeneralisation", "secondary_errors": [],
            "error_class": "single_error", "confirmed_by": "a01", "source_item": "G0098"}}
```

| Field group | Content | Scores |
| --- | --- | --- |
| `schema_version` | The version of this item schema | Reading the file |
| `claims[]` with `span` | The reference atomic claims in the text unit, fixed after claim extraction (section 5) | S1 |
| `pairs[]` | One entry per claim-source pair, each with its own `pair_id` | Unit for S2 to S5 |
| `evidence_spans` | Every passage a careful reader would accept as bearing on the claim | S2 |
| `agreement_label` | One of the four RFC-001 labels per pair, or `conflicting` when passages of the source disagree | S3, S5 |
| `scope_flags` | The flags that apply to the pair, from the seven in RFC-001 | S4 |
| `status` | One of the four scientific statuses per claim, after combining sources | S6 |
| `expert_would_review` | Whether an expert would want to check this claim personally | Human-review flag |
| `source_group` | Groups sources that are not independent (section 6) | Splitting and interval estimates |
| `annotation` | The two annotators, the adjudicator, and claim extraction: each annotator's own list of claims (`span`, `text`) and whether the list was adjudicated | Annotation quality, S1 agreement |
| claim `raw` | Each annotator's `status` and `expert_would_review` for the reference claim, stored unchanged | Annotation quality |
| pair `raw` | Each annotator's `evidence_spans`, `agreement_label` and `scope_flags` for the pair, stored unchanged | Annotation quality |
| `adjudicated` | At claim extraction, on each claim and on each pair: whether the adjudicator set the reference values at that level | Annotation quality |
| claim `ambiguous` | The claim remained disputed after joint discussion (section 5); it is excluded from the primary metrics | Reported separately |
| `hidden` | For a perturbed item: target error, secondary errors, error class, who confirmed it and the natural item it was made from. For a system-generated item: `generated_by`, the code of the system and configuration that produced it. Absent for a natural item | Never shown to annotators or to the system; used only for analysis |

`annotators` holds exactly two annotators. Wherever the two raw entries differ, `adjudicated` is true at the level where they differ: the claim lists at claim extraction, a claim's status or review flag, or a pair's labels.

The source text itself is stored once, with its hash, so the system is evaluated on exactly the text the annotators read.

## 5. Annotation

### Who annotates

- Each item is labelled by two annotators with graduate-level training in the item's domain: machine-learning items by ML researchers, biomedical items by biomedical researchers.
- Annotators are independent of the system. They have not written or tuned the verification prompts, and they do not see system output for the items they label.
- A third, senior annotator adjudicates.
- The team is small, so annotators are recruited from outside it where possible. If a team member must annotate, that person is barred from prompt and parameter tuning on the same release, and the report says so.

### Process

1. **Guideline.** A written guideline defines every label of RFC-001 with positive, negative and borderline examples, and gives a decision order: evidence spans first, then the agreement label, then scope flags, then status.
2. **Calibration round.** Both annotators label the same 30 items, discuss the disagreements, and the guideline is revised. This round is repeated until agreement is acceptable. Calibration items are not part of the released set.
3. **Claim extraction.** Each annotator lists the atomic claims of the text unit independently. Differences are adjudicated and the reference claims are fixed. Each annotator's own list is kept.
4. **Labelling.** Both annotators label the same reference claims independently: for each claim its status and whether an expert would review it; for each claim-source pair its evidence spans, source-level label and scope flags.
5. **Recording disagreement.** Both sets of labels are stored unchanged, and agreement is computed before any discussion.
6. **Adjudication.** The adjudicator reviews every claim, pair and claim list on which the annotators differ and sets the final label, with a written reason. Where the adjudicator cannot decide, the three discuss it jointly.
7. **Ambiguous items.** The `ambiguous` mark is set per claim. A claim that remains disputed after joint discussion is marked `ambiguous`. It stays in the set, is excluded from the primary metrics, and is reported separately with its count, both annotators' labels and its characteristics. The other claims of its item are kept.
8. **Freeze.** The release gets a version number and a content hash. Evaluation uses a frozen release and never changes its labels.

### Agreement measures

| Label | Measures |
| --- | --- |
| Agreement label, status | Raw agreement, the confusion table between annotators, Cohen's kappa, and Gwet's AC1 |
| Scope flags | Raw agreement, Cohen's kappa and Gwet's AC1 per flag |
| Evidence spans | Token-level overlap F1 and intersection over union between the two annotators' spans |
| Atomic claims | Share of claims matched between annotators |

Kappa alone is not enough. It is sensitive to the label distribution, so a rare label such as `contradicted` can show high raw agreement and a modest kappa. Gwet's AC1 is reported beside it as a measure that is less affected by skew.

Agreement is reported per label and per domain. A kappa of 0.6 is the initial floor, not a quality target: if a label stays below it after calibration, its definition is revised, or it is merged with a neighbour, before the main round starts. Human agreement is also the practical ceiling for the system's scores on that label.

Disagreement is a finding, not noise to be removed. Both annotators' raw labels stay in the released set after adjudication, and the report analyses where and why experts differ.

### Errors found later

A labelling error discovered after the freeze goes into an errata list with its evidence. Errata are applied only in a new release, by the adjudicator, without reference to system output. Results always state the release they were computed on.

## 6. Splits, versioning and protection of the test set

| Split | Share | Use |
| --- | --- | --- |
| `dev` | About 30% | Tuning prompts, the retrieval depth k and thresholds; error analysis |
| `test` | About 70% | Reported results only |

- **Group-aware split.** Items are split by `source_group`, not at random and not by single document. A group holds everything that is not independent: one paper under all its identifiers, its preprint and published versions, the conference and journal versions of the same study, and separate papers that report the same study or experiment where their claims would overlap closely. A whole group goes to one split.
- **Perturbed items follow their origin.** A perturbed item stays in the split of the natural item it was made from.
- **Same strata.** Both splits follow the strata of section 3.
- **Restricted access to test.** Until development for a release ends, the test split is not readable by the agents or by the developers who tune prompts. It is held by the adjudicator, and test runs are executed through a script that returns only metrics.
- **No tuning on test.** Prompts, models, k and decision rules are fixed before a test run. Every test run is logged with the protocol version, prompt versions, model IDs and the gold release.
- **Limited looks.** Test results are computed at defined points: the end of M2 on v0, and the benchmark in M4 on v1. Running the test split repeatedly while adjusting the system turns it into a second dev set.
- **Fresh items.** System-generated items for a release are sampled after the system configuration for that release is fixed, so the system has not been tuned on them.
- **Versioning.** Releases follow `major.minor`. A change of label definitions or strata is a major release; errata are a minor release. Each release has a content hash and a changelog.
- **Model contamination.** Natural claims come from published papers that a model may have seen in training. Perturbed and system-generated items are new text, and results are reported per item source so that any gap is visible.

## 7. Metrics

### Unit of evaluation

Each metric is computed on one stated unit. A claim with three sources is three pairs but one claim, and it is counted once in every claim-level metric.

| Unit | Identifier | Metrics computed on it |
| --- | --- | --- |
| Text unit | `item_id` | S1 |
| Claim-source pair | `pair_id` | S2, S3, S4, S5 |
| Claim | `claim_id` | S6, the human-review flag, and the four headline metrics |
| Source group | `source_group` | Not scored; the cluster for splitting and for interval estimates |

Scope flags are scored per pair, because a flag compares a claim with one source's evidence. The union of flags per claim is reported as a secondary view.

### Definitions

For any label c, an item counts as a true positive (TP) when the system and the reference both assign c, a false positive (FP) when only the system does, and a false negative (FN) when only the reference does.

| Metric | Formula |
| --- | --- |
| Precision of c | TP / (TP + FP) |
| Recall of c | TP / (TP + FN) |
| F1 of c | 2 × precision × recall / (precision + recall) |
| Macro-F1 | Unweighted mean of F1 over all labels |
| False-positive rate of c | FP / (number of items whose reference label is not c) |

Macro-F1 is used because the set is stratified and the labels matter equally; accuracy alone would hide weak labels.

### Headline metrics

These four numbers summarise whether the protocol can be trusted. They are computed on claim status, the output of S6.

| Metric | Definition | Why it matters |
| --- | --- | --- |
| False-verified rate | Of the claims the system marks `verified`, the share whose reference status is not `verified`. Equal to 1 minus the precision of `verified` | The main risk: an unsupported claim passing as supported |
| Critical miss rate | Of the claims whose reference status is `contradicted`, the share the system marks `verified` | The most harmful single error |
| Verified coverage | Of the claims whose reference status is `verified`, the share the system marks `verified`. Equal to the recall of `verified` | A checker that verifies nothing is safe and useless |
| Review load | Share of all claims the system sends to human review | The human cost of the safety |

RFC-001 called the first of these the false-positive rate of `verified`. This RFC names it false-verified rate to avoid confusion with the standard false-positive rate, and reports both.

Two cautions apply to the headline metrics.

- **Dependence on the status mix.** The false-verified rate depends on how many unsupported claims the set contains, and the stratified set contains far more than real output does. It is therefore reported twice: on the stratified test split, and re-weighted to the status mix observed in system-generated items.
- **Operational failures.** A claim the system leaves `unverified` is not a wrong answer and not a right one. The failure rate, meaning the share of claims left `unverified` and the reasons, is reported beside the headline metrics, and such claims count against verified coverage.

### Per-step metrics

| Step | Unit | Matching rule | Metrics |
| --- | --- | --- | --- |
| S1 | Text unit | A predicted claim matches a reference claim when their spans overlap by at least half and both carry the same citations | Precision and recall of claims |
| S2 retrieval | Pair | A reference evidence span is found when a retrieved passage contains it | Recall at k |
| S2 selection | Pair | A selected passage is correct when it overlaps a reference span | Precision and recall of passages; share of quotes that pass the string check |
| S3 and S5 | Pair | Exact match on the five source-level labels | Per-label precision, recall and F1; macro-F1; confusion table; kappa between S3 and S5 |
| S4 | Pair | Each flag is scored as its own yes-or-no label | Per-flag precision, recall and F1; micro and macro averages |
| S6 | Claim | Exact status match | Per-status precision, recall and F1; macro-F1; the four headline metrics |
| Human-review flag | Claim | Compared with `expert_would_review`, and with whether the automatic status was wrong | Share of wrong automatic statuses that were flagged; review load |

Later steps are scored twice: end to end, and with reference inputs from the earlier steps. The second score shows how good a step is on its own, and the difference shows how much error it inherits.

### Other components

| Component | Metrics |
| --- | --- |
| Citation existence | Precision and recall of detecting invalid references; false-alarm rate on real references |
| Numeric traceability | Precision and recall of detecting a wrong or misattributed number, by error type |
| Methodological errors | Detection rate and false-alarm rate of the reviewer agents, by error type |

## 8. Evaluation procedure, thresholds and accepted defaults

### Procedure

1. Fix the system configuration and log it.
2. Run the full test split three times, because model output can vary even at temperature 0. Report the mean and the range.
3. Compute every metric of section 7 on its stated unit. Exclude `ambiguous` claims from the primary numbers and report them separately, with their count and characteristics.
4. Report two 95% intervals for the false-verified rate and the critical miss rate: an exact binomial interval, which stays valid when a stratum is small or no error is observed, and a cluster bootstrap that resamples by `source_group`, since claims from one paper are not independent. Other metrics use the cluster bootstrap.
5. Break results down by domain, item source, evidence text (abstract or full text), hard-case group and error class.
6. Compare configurations on the same items with a paired test.
7. Publish the full confusion tables, the failures, the failure rate and the cost per claim, not only the summary numbers.

### Baselines for the protocol itself

| Baseline | What it shows |
| --- | --- |
| One model, one prompt: is this claim supported by this source? | Whether six steps beat the simplest approach |
| S1 to S3 only, no scope check and no second assessor | What S4 and S5 add |
| Full protocol with the same model in S3 and S5 | What a different model family adds |
| Human agreement | The practical ceiling |

### Proposed thresholds for hypothesis H3

The thresholds below are initial targets. They are fixed in three stages:

1. The v0 pilot is used to calibrate the annotation guideline, measure human agreement and estimate the sample sizes needed. Its results may inform the thresholds.
2. The final thresholds for H3 are recorded and locked after the v0 pilot and before the first run on the v1 test split.
3. After v1 test results have been seen, the thresholds do not change.

| Metric | Unit and denominator | Initial target on the v1 test split |
| --- | --- | --- |
| False-verified rate | Claims the system marks `verified` | At most 5%, with the upper end of the 95% interval at most 10% |
| Critical miss rate | Claims whose reference status is `contradicted` | At most 2% |
| Verified coverage | Claims whose reference status is `verified` | At least 60% |
| Macro-F1 of status | All non-ambiguous claims, four statuses | At least 0.70 |
| Review load | All claims | At most 25% |

A threshold is met only if the stated interval condition holds, and comparisons between configurations rest on the paired test of the procedure above.

If the thresholds are missed, the result is reported as it is. H3 is then not supported, and the thresholds are not moved afterwards.

### Accepted defaults

| Topic | Accepted default |
| --- | --- |
| Sizes of about 150 and 600 claims | Kept; statistical adequacy is checked after the pilot |
| Annotators and compensation | Two independent annotators per domain and one senior adjudicator, compensated by time and expertise |
| Kappa floor | 0.6 as an initial minimum, reported with raw agreement and Gwet's AC1 |
| H3 thresholds | Locked after the pilot and before the v1 test run |
| Publication of the set | `dev` and `test` published with version and hash, within the terms of each source's licence |
| SciFact | A secondary, external check of generalisation; its labels are not merged into the gold set |

### Next step

RFC-001 and RFC-002 together define the two main research contributions: the method for checking claim support, and the independent reference set that tests it. Work now moves from documents to building v0, running the first experiments and studying the errors the system actually makes. The architecture is not extended before those first results are in.
